1 Overview
Reth에 Commonware 합의 엔진을 통합한 이유와 구조

Reth (Execution Layer)

Rust로 작성된 고성능 Ethereum 실행 클라이언트. 트랜잭션 실행, 상태 관리, RPC 서비스 등 EVM 실행 레이어 전체를 담당합니다.

  • MDBX + Static Files 하이브리드 스토리지
  • Parallel EVM 실행 (rayon 기반)
  • Engine API (newPayload, forkchoiceUpdated)
  • JSON-RPC (eth, net, web3, debug, txpool)

Commonware SimplexBFT (Consensus Layer)

BFT 기반 합의 프로토콜. Beacon Chain을 대체하여 블록 제안, 투표, Finalization을 수행합니다.

  • BLS12-381 Threshold Signature (2/3+ 서명)
  • VRF 기반 리더 선출
  • Epoch 단위 합의 관리 (100 blocks/epoch)
  • Instant Finality (투표 즉시 확정)

3 Consensus Flow
블록 제안부터 Finalization까지의 합의 프로세스
1

VRF Leader Election Epoch Manager

매 View(블록)마다 BLS12-381 VRF을 사용하여 검증자 중 한 명을 리더(Proposer)로 선출합니다.
리더 선출은 결정론적이지만 예측 불가능하여 MEV 공격을 방지합니다.

2

Block Building ~1000ms sleep Application Actor

a) 리더가 EL에 forkchoiceUpdated 전송 (PayloadAttributes 포함)
b) time-to-build-proposal (1000ms) 동안 sleep → txpool에서 트랜잭션 수집 대기
c) EL의 Payload Builder가 블록 조립 + EVM 실행 완료
d) newPayload로 블록을 EL에 등록 후, digest를 네트워크에 브로드캐스트

3

Voter Verification wait-for-proposal 내 All Validators

모든 검증자가 proposal을 수신하고 application.verify() 실행:
a) P2P broadcast로 블록 데이터 수신
b) 블록 RLP 디코딩 + 부모 블록 확인
c) EL에 newPayload 전달 → EVM 실행으로 유효성 검증
d) 유효하면 BLS12-381 threshold share로 서명하여 vote 전송

4

Notarization & Finalization Marshal

2/3+ (N=4일 때 3개) 검증자 서명이 모이면 threshold certificate 생성.
Marshal이 certificate를 검증하고 블록을 immutable archive에 저장.
Instant Finality — 이 시점에서 블록은 되돌릴 수 없이 확정됩니다.

5

EL State Update Executor

Executor가 EL에 forkchoiceUpdated 전송:
{ head_hash, safe_hash, finalized_hash } 모두 새 블록으로 설정.
EL이 상태를 영구 저장하고 다음 블록 빌드 준비.

6

Epoch Transition 매 100 블록 DKG Manager

block.number % epoch_length(100) == 0 감지 시:
현재 epoch의 SimplexBFT 인스턴스 종료 → 다음 epoch 인스턴스 시작.
동일 검증자 셋 + 동일 threshold scheme 재등록 (Static DKG).

5 Key Timing Relationship
성능과 안정성을 결정하는 핵심 타이밍 파라미터 관계
// Block Cycle Time (블록 생성 주기) block_time = time_to_build_proposal + evm_execution + network_delay = 1000ms + ~458ms + ~200ms = ~1,658ms // Voter Safety Window (투표자가 블록을 검증할 수 있는 시간) voter_window = wait_for_proposal - time_to_build_proposal - network_overhead = 2000ms - 1000ms - ~50ms = 950ms safety_margin = voter_window / evm_execution = 950 / 458 = 2.07x // TPS Calculation (초당 트랜잭션 처리량) tps = gas_limit / gas_per_tx / block_time = 220,000,000 / 21,000 / 1.658 = ~6,316 TPS (theoretical, simple transfer) // EVM Throughput evm_speed = ~480 Mgas/s (measured on 12-core host) exec_time(220M) = 220 / 480 * 1000 = ~458ms

time-to-build-proposal 이 클수록

  • txpool에서 더 많은 tx 수집 가능
  • 블록 gas utilization 증가
  • 블록 주기 증가 (TPS 감소)
  • 리더가 불필요하게 오래 대기

wait-for-proposal 이 클수록

  • voter 검증 시간 여유 (안정성 향상)
  • 느린 노드도 참여 가능
  • nullify timeout 증가 (장애 복구 느림)
  • 리더 불참 시 빈 블록 대기 시간 증가

7 DKG & Epoch Management
검증자 키 관리와 Epoch 기반 합의 생명주기

Static Deterministic DKG

별도의 DKG 세레모니 없이, Genesis 설정의 검증자 목록과 고정 Namespace 해시를 시드로 사용하여 모든 노드가 동일한 threshold scheme을 독립적으로 생성합니다.

// Namespace seed (모든 노드 동일) seed = hash("PRIVATE_CHAIN") // Threshold scheme 생성 scheme = dkg::deal(seed, validators, N3f1) // N3f1 = ceil(2n/3) threshold // 4 validators → 3-of-4 필요 // 각 노드가 자신의 BLS share 추출 my_share = scheme.shares[my_index]

Epoch Lifecycle

100 블록 단위로 Epoch가 전환되며, 각 Epoch마다 독립적인 SimplexBFT 인스턴스가 실행됩니다.

Epoch 0 Block #1 ~ #100
Epoch 1 Block #101 ~ #200
Epoch N Block #(N*100+1) ~ #((N+1)*100)
Transition height % 100 == 0 → Exit + Enter
